- `metrika-report` (`seo_metrika_report`) and `MetrikaClient.report()`: a Reporting API
  "Query is too complicated" refusal is now retried in calendar-month slices with a 5–15 s
  backoff; a slice that still refuses is resubmitted at a sampled `accuracy=0.1`. Only
  metrics provably additive over disjoint periods (`ym:s:visits`, `ym:s:pageviews`) are
  merged — a query for unique-visitor, percentage, average, or unverifiable metrics is
  refused before the first slice request rather than returning a summed value that would
  be wrong. Merged answers re-apply the caller's `sort` (dimensions and metrics, or the
  API default of first metric descending) and take the `offset`/`limit` window from the
  global merged set under one global row cap. Sampling fields reflect what the API
  actually reported (`sampled`, worst `sample_share`); `contains_sensitive_data` is the
  OR over slices, `min`/`max` are recomputed on merged rows, and missing metric cells
  or totals mark the body `incomplete` instead of reading as zero. The `split` block
  keeps the requested and resolved periods, the timezone used, and per-slice accuracy,
  attempts, and sampling metadata; a partition that fails names the completed spans and
  the accuracies exhausted. Relative dates (`today`, `NdaysAgo`) resolve in the request
  `timezone` or the counter's own zone — never the host date. A period that cannot be
  mapped to dates (a shorthand such as `month`) is still retried and sampled before the
  error is re-raised. An explicit `accuracy` in the request params is honored instead of
  being overridden to `full`, and every attempted request — including the refused
  whole-range call — reaches the spend journal.
